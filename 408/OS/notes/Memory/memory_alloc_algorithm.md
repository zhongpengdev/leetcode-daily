# 动态分区分配算法性能因素

> 动态分区分配是早期多道程序系统的核心方案，典型如 IBM OS/360 的 MVT。它不预先划分内存区域，作业到达时才动态分割空闲块，因而具备灵活性和高内存利用率的潜力，但代价是需要复杂的数据结构跟踪空闲分区，且必须周期性地执行紧凑来应对外部碎片。
>
> 现代通用操作系统（Linux、Windows、macOS）的进程级内存分配已不再采用纯动态分区分配：页式管理方案彻底消除了外部碎片问题。但动态分区分配的思想仍活跃在内核内部的内存子系统中（buddy system、slab allocator），以及一些嵌入式实时 OS 中。
>
> 其核心思想是"分配策略 vs 碎片 vs 维护成本"的权衡逻辑。

## 两个指标 

1. 外部碎片率决定内存分配的紧凑程度

2. 以及空闲链表数据结构的维护成本：决定分配/回收耗时

## 内存紧凑程度

动态分区分配不划分固定的内存块，外部碎片是必然产生的。评价一个分配算法的优劣，看的是它产生的碎片是"能顺手喂给下一个进程的活碎片（如FF）"，还是"谁也用不了的死碎片（如BF）"。

FF 从头开始扫描整个链表，满足即可用，具备极强的再分配能力。同一块低地址的大空间（20MB）能够完美地把两次 5MB 和 10MB 的分配要求同时满足，同时产生最少的外部碎片。

而 BF 算法在同样的过程中会产生更多的外部碎片。它追求每次浪费最少，结果留下的空洞越来越小，最终汇聚成大量无法满足任何请求的微孔，导致接下来的大内存作业无法得到足够的内存，提前使得内存"不紧凑"，浪费 CPU 周期。经典教材均指出 BF 在外部碎片方面的表现实际上最差。

## 分区链表的数据结构维护成本 

### 分配

动态分区分配的数据结构维护成本，在于操作系统执行"分配"和"回收"两个动作时对空闲分区链表的操作复杂度，这是分配算法性能的另一个重要指标。

地址递增排序（FF、NF）在分配路径上的维护成本是 $O(1)$。一个原本在低地址的 50MB 空闲块被切走了 20MB，剩下的 30MB 虽然变小了，但它的物理地址依然在原来的区间内。系统只需要就地修改这个结构体节点的 `Address = 原Address + 20MB`、`Size = 30MB` 即可，整个链表的指针先后拓扑结构不需要发生任何改变。

大小排序（BF、WF）在分配路径上的维护成本是 $O(n)$。BF 链表原本按大小从小到大排，一个排在队伍中段的 50MB 块被切走 49MB 后只剩 1MB，大小发生了质的变化，必须重新插入到大小排序的正确位置。单次分配的链表维护成本到了 $O(n)$ 的级别。

### 回收

但，地址序维护成本 $O(1)$ 只算了一半账。回收路径上，地址序和大小序都是 $O(n)$。

无论按什么排序，回收时都要遍历链表找到正确的位置（按地址或是按大小）来插入新空闲块，同时检查能否与前后相邻的空闲块合并。

- 地址递增排序（FF、NF）：分配 O(1)，回收 O(n)
- 大小排序（BF、WF）：分配 O(n)，回收 O(n)

BF 不仅碎片问题最严重，分配和回收两端都要 $O(n)$ 维护，是综合代价最高的选择。FF 分配极快，回收 $O(n)$ 尚可接受，是简单场景下最均衡的方案。

## 工程实践

现代操作系统普遍采用更高效的数据结构。

Linux 内核用 Buddy System 管理物理页框，分配回收只需 O(log n)。内核对象的分配再用 Slab Allocator 在其上做缓存，针对固定大小的对象预分配，从根本上消除外部碎片。用户态的 malloc/free 内部也不光是链表，而是用红黑树、tcache（线程局部缓存）等结构混合。
