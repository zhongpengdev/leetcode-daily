# 软件工程 — 上帝视角

写代码容易，写**好**代码难。软件工程就是研究如何让代码**可维护、可扩展、可测试**。

从三个维度理解：

```
                    ┌──────────────────────┐
                    │   指导原则 (怎么想)    │
                    │  做决策时的心理模型     │
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │   架构模式 (怎么分)    │
                    │  系统怎么拆、怎么组织    │
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │   设计模式 (怎么写)    │
                    │  具体场景的代码套路     │
                    └──────────────────────┘
```

## 一、指导原则 — 写代码时的"心法"

决定**做不做**、**怎么权衡**。

- [KISS](KISS.md) — 能简单就简单，不要过度设计
- [DRY](DRY.md) — 不要重复，相同逻辑只写一次
- [YAGNI](YAGNI.md) — 不要实现现在不需要的功能
- [SRP](SRP.md) — 一个模块只做一件事
- [Separation of Concerns](Separation_of_Concerns.md) — 按关注点分层，各管各的
- [Law of Demeter](Law_of_Demeter.md) — 只和直接朋友通信
- [高内聚低耦合](cohesion_and_coupling.md) — 把相关的聚一起，把无关的隔离开

它们之间的关系：

```
YAGNI（决定做什么）
  └→ KISS（保持简单）
      └→ DRY（消除重复）
          └→ SRP / SoC（组织结构）
              └→ 高内聚低耦合（衡量好坏的标准）
                  └→ Law of Demeter（降低耦合的具体规则）
```

## 二、架构模式 — 系统怎么拆

决定**代码怎么组织**、**职责怎么分配**。

### 分层架构

```
Handler (表现层)  →  Service (业务层)  →  Repository (数据层)
    │                    │                     │
  HTTP请求响应        业务逻辑/规则          数据的增删改查
```

每一层只和相邻层通信，不跨层。

### 相关概念

- [SoC — 关注点分离](Separation_of_Concerns.md) — 分层的理论基础
- [IoC / DI — 控制反转 / 依赖注入](IoC_DI.md) — 层与层之间怎么解耦
- [高内聚低耦合](cohesion_and_coupling.md) — 分层好坏的衡量标准

### 横切关注点

不是某一层的事，而是**贯穿所有层**的事：

- [AOP — 面向切面编程](AOP.md) — 日志、权限、事务、监控怎么统一处理
- [Middleware — 中间件](Middleware.md) — AOP 在 HTTP 层的具体实现
- [ORM — 对象关系映射](ORM.md) — 数据层简化数据库操作的工具

```
          ┌─────────────────────────────────┐
          │  日志 / 权限 / 事务 / 缓存 / 限流  │  ← AOP 横切
          ├───────────┬───────────┬─────────┤
          │  Handler  │  Service  │  Repo   │
          └───────────┴───────────┴─────────┘
```

## 三、设计模式 — 具体怎么写

决定**某个具体问题用什么代码套路**。

- [设计模式总览](Design_Patterns.md) — GoF 23种模式精要 + Go 实现

按三大类分：

| 类型 | 模式 | 解决什么问题 |
|------|------|-------------|
| 创建型 | 工厂模式 | 不直接 new，根据条件创建不同类型 |
| 创建型 | 单例模式 | 全局只有一个实例 |
| 结构型 | 适配器模式 | 接口不匹配时做转换 |
| 结构型 | 装饰器模式 | 动态给对象添加功能 |
| 行为型 | 策略模式 | 算法可以灵活切换 |
| 行为型 | 观察者模式 | 一对多通知，事件驱动 |

## 学习顺序建议

1. **先学原则**：KISS → DRY → YAGNI → SRP → SoC → 高内聚低耦合
2. **再学架构**：分层 → IoC/DI → AOP → ORM → Middleware
3. **最后学模式**：先学最常用的工厂、策略、观察者，其他按需学
